# TDD-цикл для CatalogService (SCRUM-6)

## Вимоги

Сервіс каталогу працює через абстрактний `ICatalogRepository`, окремо від бази даних. Він додає авторів, категорії, книги та примірники, перевіряє пов’язані сутності та зберігає зміни через репозиторій.

Інвентарні номери порівнюються точно з урахуванням регістру. Сервіс не нормалізує номери.

## Red

Фактичний запуск Test Explorer для всього рішення показав:

- 37 тестів усього рішення;
- 28 успішних;
- 9 невдалих тестів `CatalogServiceTests`.

Усі попередні тести залишалися успішними. Невдалими були сценарії заглушки `CatalogService`, які очікували реального додавання сутностей і перевірки помилок.

## Green

Реалізація `CatalogService` має:

- перевірку `repository` на `null`;
- створення валідних сутностей через доменні конструктори;
- перевірку відомої категорії та авторів;
- `ArgumentException` для невідомої категорії або автора;
- `ArgumentNullException` для `null authorIds` та порожню перевірку для порожнього списку;
- усунення повторів `authorIds` через `Distinct`;
- `KeyNotFoundException` для невідомої книги;
- точну перевірку інвентарного номера з урахуванням регістру;
- `DuplicateInventoryNumberException` для дубля номера;
- єдине збереження після успішного додавання;
- відсутність мутацій репозиторію до завершення перевірок.

Green фактично перевірено через Test Explorer: усі 40 тестів усього рішення пройшли, 0 помилок, 0 пропусків. Із них 39 тестів належать до `Library.UnitTests` (один із них шаблонний), а 1 тест належить до `Library.IntegrationTests` і є шаблонним. Реальні інтеграційні перевірки бази даних ще не реалізовані.

## Refactor

Структуру перевірок у реалізації `CatalogService` переглянуто: зайвих абстракцій і ускладнень не додано. Перевірки залишені зрозумілими й послідовними, а мутації репозиторію виконуються лише після повного успішного сценарію.

## Унікальність номери

Сервіс перевіряє дубль через репозиторій, але сам по собі не гарантує конкурентну унікальність. Конкурентну унікальність забезпечить майбутній унікальний індекс бази даних у рівні інфраструктури.

## Роль GitHub Copilot

GitHub Copilot підготував Red-тести з in-memory фейком, реалізував перевірки й безпечний порядок мутацій у `CatalogService` та зафіксував вимоги в документації SCRUM-6.
